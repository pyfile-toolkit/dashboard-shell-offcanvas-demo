# Dashboard shell demo — responsive Offcanvas (Bootstrap 5.3)

[![tests](https://github.com/pyfile-toolkit/dashboard-shell-offcanvas-demo/actions/workflows/test.yml/badge.svg)](https://github.com/pyfile-toolkit/dashboard-shell-offcanvas-demo/actions/workflows/test.yml)

Минимальное публичное демо оболочки дашборда: одна разметка, которая на узком экране
работает как Bootstrap Offcanvas, а от `768px` — как статичная колонка. Здесь нет
бэкенда, роутер — хэш-роутер, содержимое страниц — заглушки. Всё, что есть, существует
ради одного: **показать, как я проверяю поведение меню, фокуса и брейкпоинтов**, а не
рассказать об этом словами.

Демо собрано под конкретный вопрос заказчика по этапу M4 (Dashboard Shell): как будут
проверяться Offcanvas (фокус, Esc/backdrop, закрытие при навигации, смена mobile/desktop)
и где в этом месте QA-матрица.

## Запуск

```bash
npm ci
npx playwright install --with-deps   # chromium, firefox, webkit
npx playwright test                  # 3 браузера × spec ниже
npx playwright show-report           # HTML-отчёт с трейсами упавших кейсов
```

Открыть вручную: `index.html` в браузере (Bootstrap подключается с CDN, нужен интернет).

## Что именно проверяется (и почему именно это)

| # | Утверждение | Почему проверяем |
|---|---|---|
| 3.1 | Матрица: оболочка рендерится на 360/390/576/768/1024/1440, кнопка меню существует только до `768px`, панель в DOM одна | Две копии меню (мобильная и десктопная) — типовой источник рассинхрона; проверяем, что разметка одна |
| 3.2 | Фокус внутри панели при открытии, Tab и Shift+Tab не выводят фокус наружу, Esc закрывает, после закрытия фокус возвращается на триггер | Offcanvas — модальный диалог, а не «выехавший блок»: уход фокуса на фон ломает и клавиатуру, и скринридер |
| 3.3 | Клик по подложке закрывает, после закрытия `.offcanvas-backdrop` не остаётся, `body.overflow` чист | Залипшая подложка = страница «мертва» для кликов до перезагрузки |
| 3.4 | Клик по пункту меню закрывает панель, маршрут меняется, breadcrumbs строятся из метаданных маршрута, следов не остаётся | Bootstrap не связывает offcanvas с роутером: в SPA панель остаётся открытой поверх новой страницы, если это не сделать явно |
| 3.5 | Смена ширины **в открытом состоянии**: панель не остаётся диалогом, подложка и scroll-lock не переживают переход, `aria-modal`/`role` снимаются, обратный переход возвращает нормальное поведение | Самый ломкий кейс адаптивного offcanvas: класс `offcanvas-md` переключается, а «хвосты» модальности — нет |

Матрица приёмки (6 маршрутов × 3 браузера × 6 ширин) в этом демо разложена так:
браузеры — проекты Playwright (`playwright.config.js`), ширины — в spec, маршруты —
`ROUTES` в `app.js` (шесть маршрутов из ТЗ M4 продублированы один в один, чтобы демо
и приёмка говорили об одном и том же).

## Что нашлось по ходу (измерения, а не мнения)

1. **FocusTrap у Offcanvas есть только с 5.3.** В `bootstrap.esm.js` 5.3.3 конструктор `Offcanvas` вызывает
   `this._focustrap = this._initializeFocusTrap()` с `trapElement: this._element`. На 5.0–5.2 этого не было:
   там фокус не удерживался, и поведение пришлось бы писать руками. Отсюда правило — версия Bootstrap
   фиксируется в проекте, а не берётся «примерно пятая».
2. **Фокус приходит в панель ПОСЛЕ перехода, а не при открытии.** Замер в Firefox (200/600/1200 мс):
   на 200 мс класс ещё `showing` и активна кнопка меню, на 600 мс активна сама панель. Первая версия
   теста проверяла фокус сразу после появления класса `show` и падала на здоровом коде — это была
   гонка в тесте, а не дефект. Поэтому проверки фокуса идут через ожидание (`expect.poll`).
3. **Клик по подложке легко проверить неправильно.** Панель шириной 260 px занимает левый край окна:
   клик в координату (8, 8) попадает по самой панели, а не по подложке, и тест «успешно» проваливается
   на работающем коде. Точка клика берётся заведомо вне панели.
4. **Смена брейкпоинта оставляет «хвосты».** В открытом состоянии при переходе mobile → desktop у
   адаптивного offcanvas остаются подложка, блокировка скролла и `aria-modal`. Класс `offcanvas-md`
   переключает разметку, но не убирает модальные следы — это делает `reconcileBreakpoint()`.

## Устройство

- `index.html` — оболочка: topbar, sidebar (`offcanvas-md`), breadcrumbs, слот содержимого.
- `app.js` — route registry (единственный источник правды для меню, breadcrumbs и заголовка),
  закрытие панели при навигации, `reconcileBreakpoint()` (уборка после смены ширины),
  возврат фокуса на триггер.
- `tests/offcanvas.spec.js` — пять тестов выше.
- `playwright.config.js` — три браузера, HTML-отчёт, трейс на падение.
- `vendor/` — Bootstrap 5.3.3 (CSS + JS, лицензия MIT сохранена в файлах).

### Почему Bootstrap лежит в репозитории, а не приходит с CDN

Изначально страница собиралась ссылками на `cdn.jsdelivr.net`. Замер показал, что при этом дважды меняется смысл проверки.

1. **Тесты проверяют не наш артефакт, а чужой сервер.** Пока стили и JS грузятся извне, «спека зелёная» означает «в момент запуска у jsDelivr всё было хорошо». В браузере без доступа к CDN страница отдаётся без стилей, панель не открывается — а тест формально может успеть до загрузки и выглядеть пройденным (или упасть по чужой причине). Первый признак нашёлся именно так: скриншот страницы пришёл неоформленным, хотя с хоста CSS отдавался `200` за `0.27 с`.
2. **Нарушение не в поведении, а в том, чему верим.** Поэтому ссылки заменены на локальные файлы (`vendor/bootstrap.min.css`, `vendor/bootstrap.bundle.min.js`), а шрифтовая иконка бургера — на один inline SVG: тот же принцип, что и с CDN, но теперь у демо ноль внешних загрузок во время теста.

Артефакт: после замены `npx playwright test` → `15 passed (17.2s)` при отключённой сети к jsDelivr.

## Что здесь сознательно не сделано

- Нет бэкенда, авторизации, RBAC и хранения состояния — по границам задачи это в этап не входит.
- Нет стилизации «под продукт»: важен каркас и поведение, а не внешний вид.
- Нет обхода чужих требований, ТЗ или фрагментов коммерческого кода: демо написано с нуля
  и не содержит ничего из материалов заказчика.
